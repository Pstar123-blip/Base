# Working Conventions

Conventions for working in this repo. Follow them when adding or changing code.

## 1. Folder structure (client)

Code is organized by **feature**. A feature folder contains only the subfolders it actually needs, chosen from:

| Folder       | Contents                                      |
| ------------ | --------------------------------------------- |
| `hooks/`     | Custom hooks (non-API logic)                  |
| `components/`| Feature-specific components                   |
| `queries/`   | Query-related code (not API hooks, see §4)    |
| `mutations/` | Mutation-related code (not API hooks, see §4) |
| `pages/`     | Route-level pages                             |
| `utils/`     | Pure helpers                                  |

Do not create empty folders or folders outside this list without a reason.

## 2. Constants

Put constants in designated consts files (e.g. `consts.ts`) at the appropriate scope: next to the code that uses them, or at the feature/shared level if multiple files use them. Avoid inline magic values.

## 3. Styling components

Do not use `sx` to style components inside a component. Instead create a styled MUI component (`styled(...)`) in a dedicated file at the same scope:

- Component `A` → `A.styles.tsx`, next to `A.tsx`
- Create the styles file only when the component needs styling.

## 4. API communication (client)

Do not write new hooks for API communication. Use the hooks generated by Orval (`client/src/api/generated/`). Regenerate with `npm run generate` in `client/` after API changes. Never edit generated files by hand.

## 5. API annotations (api)

Types are generated from the API's OpenAPI spec (`api/openapi.json`), so every controller and DTO must carry proper `@nestjs/swagger` `@Api*` annotations (e.g. `@ApiTags`, `@ApiProperty`, `@ApiOperation`, `@ApiOkResponse`, `@ApiBody`). Without them, generated types and hooks will be missing or wrong. After changing endpoints or DTOs, regenerate the spec and the client.
